### **Название задачи:** ADR-1: Архитектура MVP онлайн-подачи заявок на депозит
### **Автор:** Архитектурный комитет банка "Стандарт"
### **Дата:** 30.09.2025
### **Функциональные требования**

Основные Use Cases для MVP:

|**№**|**Действующие лица или системы**|**Use Case**|**Описание**|
| :---: | :--- | :--- | :--- |
| UC1 | Новый клиент, Сайт, Система кол-центра | Подача заявки на депозит новым клиентом | 1. Пользователь заходит на Сайт, видит список депозитов. 2. Пользователь выбирает депозит и заполняет форму (ФИО, телефон). 3. Сайт передает заявку в Систему кол-центра. 4. Сотрудник кол-центра связывается с клиентом для дальнейших шагов. |
| UC2 | Существующий клиент, Интернет-банк, СМС-шлюз, АБС | Подача заявки на депозит существующим клиентом | 1. Клиент авторизуется в Интернет-банке, видит общие и персональные ставки. 2. Клиент выбирает депозит, счет списания и сумму, подает заявку. 3. Интернет-банк запрашивает подтверждение операции через СМС. 4. Клиент вводит СМС-код, заявка отправляется на обработку в АБС. |
| UC3 | Сотрудник бэк-офиса, АБС | Ручная обработка заявки | 1. Сотрудник бэк-офиса видит в АБС новую заявку от клиента. 2. Сотрудник проверяет данные и подтверждает открытие депозита в АБС. |
| UC4 | Клиент, АБС, СМС-шлюз | Уведомление клиента об открытии депозита | 1. После подтверждения заявки в АБС система инициирует отправку СМС. 2. Клиент получает СМС-уведомление об успешном открытии депозита. |

### **Нефункциональные требования**

Ключевые архитектурно значимые требования, влияющие на решение:

|**Код**|**Требование**|
| :---: | :--- |
| R2, R3 | Высокая доступность (99,9%) и отказоустойчивость к сбою ЦОД. |
| P2 | Поддержка горизонтального масштабирования новых компонентов. |
| +R3 | Новая логика СМС-подтверждений должна быть реализована силами банка. |
| +R4 | Избегать прямой синхронной нагрузки на АБС со стороны интернет-банка. |
| +R5 | Архитектура должна учитывать, что АБС масштабируется только вертикально. |
| +R6 | Для асинхронного взаимодействия использовать Apache Kafka. |
| +R7 | Новую функциональность в интернет-банке реализовывать в рамках микросервисной архитектуры. |

### **Решение**

Для реализации MVP выбрана микросервисная архитектура с асинхронным взаимодействием через брокер сообщений Apache Kafka. Это позволяет изолировать новый, масштабируемый функционал от унаследованной системы АБС, обеспечив при этом высокую надежность и производительность.

### **Альтернативы**

1.  **Прямая синхронная интеграция с АБС через API.**
    * *Причина отказа:* Высокий риск перегрузки и отказа АБС, что противоречит требованиям **+R4** и **+R5**.
2.  **Доработка существующего монолита интернет-банка.**
    * *Причина отказа:* Не соответствует стратегическому решению о переходе на микросервисную архитектуру (**+R7**), усложняет горизонтальное масштабирование (**P2**) и не решает проблему с несовместимостью с Kafka.

### **Недостатки, ограничения, риски**

* **Повышенная сложность:** Внедрение микросервисной архитектуры и Kafka увеличивает операционную сложность по сравнению с доработкой монолита.
* **Конечная консистентность:** Из-за асинхронной природы взаимодействия клиент не получит мгновенного подтверждения открытия депозита. Интерфейс должен корректно обрабатывать промежуточные статусы («Ваша заявка в обработке»).
* **Требования к экспертизе:** Команде потребуется экспертиза в Apache Kafka и микросервисной архитектуре.
